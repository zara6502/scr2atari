**Оценка кода GTC 0.2**

Код довольно зрелый для экспериментального компрессора. Видно, что автор уже прошёл несколько итераций (есть версии 6/7 архивов, оптимизатор грамматики, DP для таблицы длин Хаффмана).

### Сильные стороны

- **Чистая архитектура**: разделение на dictionary / huffman / table / encoder / decoder.
- **Хороший оптимизатор грамматики**: greedy Re-Pair-подобный проход + beam-search с Shannon-оценкой и точным Huffman-пересчётом. Это уже не примитивный greedy.
- **Умная таблица длин кодов** (`GtcLengthTable`): несколько моделей (RAW, CONSTANT, BITMAP, SPARSE, DELTA, DELTA_SIGNED) + DP по сегментам. Это сильная сторона.
- **Поддержка архивов** с автоматическим выбором global vs delta-Huffman.
- **Ограничение токенов 16 битами** (правила хранятся как `uint16_t left/right`) — практичный компромисс.

### Слабые места (влияющие на степень сжатия)

1. **Начальный grammar builder слишком жадный и простой**
   - Берётся только самая частая пара (классический Re-Pair).
   - Минимальный порог = 3 вхождения.
   - Нет учёта стоимости самого правила (4 байта) и влияния на модель Хаффмана.
   - Нет look-ahead и нет возможности «откатывать» плохие правила.

2. **Оптимизатор ограничен**
   - Beam width всего 4 (`OPT_PAYLOAD_BEAM` / `OPT_TOTAL_BEAM`).
   - Кандидатов только 64, точных Huffman-проверок — 24.
   - Работает только поверх уже построенной грамматики (не перестраивает её с нуля).
   - Не рассматривает правила длиннее 2 (только пары).

3. **Нет контекстной модели**
   - После построения грамматики идёт обычный статический Huffman по токенам.
   - Нет order-1 / order-2, нет ANS, нет арифметики.

4. **Ограничение 16-бит токенов**
   - Максимум ~65k правил. На больших файлах это начинает мешать.

5. **Нет предварительной обработки**
   - Нет delta-кодирования, нет RLE, нет разделения на каналы (полезно для изображений/аудио).

### Предложения по улучшению степени сжатия (по приоритету)

#### 1. Улучшить начальный grammar construction (самое важное)

Вместо чистого «самая частая пара»:

- Использовать **cost-aware** выбор:  
  `benefit = (count-1) * avg_symbol_cost - rule_cost`
- Добавить **несколько кандидатов** на каждой итерации (top-K) и выбирать по реальной оценке размера.
- Разрешить правила с 3+ символами (или хотя бы triple) для очень частых паттернов.
- Сделать adaptive threshold вместо жёсткого `count < 3`.

#### 2. Более сильный оптимизатор

- Увеличить beam (хотя бы до 16–32) и количество кандидатов.
- Добавить возможность **удаления** плохих правил (сейчас только добавление).
- Периодически делать полный re-parse последовательности с текущей грамматикой (сейчас замены только left-to-right non-overlapping).
- Рассмотреть **local search**: swap / replace существующих правил.

#### 3. Лучшая энтропийная модель после грамматики

Самый большой потенциал после улучшения грамматики:

- Перейти с Huffman на **rANS** или арифметику (особенно с order-1).
- Добавить **order-1** (или даже order-2) модель по токенам.
- Можно оставить Huffman как быстрый режим, а rANS — как максимальный.

#### 4. Предварительная обработка

- Для текстовых/бинарных данных: delta + RLE.
- Для изображений (если цель — ZX/Atari арты): разделение на bitplanes / преобразование в более удобный порядок байтов.
- Простой XOR с предыдущей строкой (очень помогает на картинках).

#### 5. Более компактное хранение грамматики

Сейчас каждое правило — 4 байта (`uint16_t` + `uint16_t`). Можно:

- Кодировать правила через ту же Huffman/длины.
- Использовать дельты или reference coding для часто встречающихся left/right.
- Разделять «горячие» и «холодные» правила.

#### 6. Разные режимы сжатия

Сделать несколько пресетов:

- Fast (текущий greedy + небольшой beam)
- Normal
- Max (большой beam + rANS + order-1 + более агрессивный grammar)

### Ожидаемый эффект

| Улучшение                        | Прирост сжатия (примерно) | Сложность |
|----------------------------------|---------------------------|---------|
| Cost-aware grammar + top-K       | +5–15%                    | Средняя |
| Больший beam + удаление правил   | +3–8%                     | Средняя |
| rANS / order-1                   | +8–20%                    | Высокая |
| Предварительная обработка        | сильно зависит от данных  | Низкая–средняя |
| Компактная грамматика            | +2–6%                     | Средняя |

### Итог

Код уже находится на хорошем уровне для «домашнего» grammar-компрессора. Основной потолок сейчас — качество самой грамматики и слабая энтропийная модель после неё.

Самые выгодные следующие шаги:
1. Сделать grammar construction cost-aware.
2. Усилить оптимизатор (больше beam + возможность удаления правил).
3. Добавить rANS + order-1 как опцию максимального сжатия.

Если хочешь, могу подробнее расписать конкретные изменения в `buildGrammar` / `optimizeGrammar` или набросать, как лучше интегрировать rANS.
